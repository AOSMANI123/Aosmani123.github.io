Seven-agent system for executive engagement operations

I designed and deployed a multi-agent orchestration system that manages 200+ executive engagement items — from intake through triage, briefing production and knowledge retrieval — with a human in the loop at every decision point.

Built 2025Role Business Manager / CEO CommunicationsStack Multi-agent orchestrationImpact 200+ items managed

Short version. A CEO's office receives hundreds of engagement requests — speaking invitations, customer meetings, events, media inquiries. I built a system of seven specialized AI agents that handles intake, triage, scheduling, briefing production, coverage evaluation and knowledge retrieval. Each agent has one job. An orchestrator routes work between them. A human reviews every output before anything leaves the system.

The problem

A CEO's office fields a constant stream of requests for the executive's time. Before this system existed, the workflow looked like this:

BeforeWhat it meant
Requests tracked in email threads and spreadsheetsNo single source of truth. Requests updated in multiple places, or not at all
Every request read and processed manuallyHigh time cost per item, details missed under volume
Briefing documents assembled from scratch each timeHours of research repeated for recurring topics and contacts
No systematic way to evaluate briefing completenessCoverage gaps discovered only when the executive asked a question nobody had an answer to
No structured knowledge base across engagementsInstitutional memory lived in individuals' heads and scattered files

The volume alone — 200+ items — made manual processing unsustainable. But the real problem wasn't volume. It was that every engagement touched multiple steps (intake, scoring, scheduling, briefing, evaluation), and those steps were handled by different people with no shared system connecting them.

The architecture

Seven agents, each with a single responsibility, coordinated by an orchestrator. The diagram below shows how work flows through the system.

Solid arrows show the primary data flow. Dashed lines show orchestrator coordination — routing tasks, handling retries, managing failures. The human review step sits at the end of every path.

What each agent does

AgentInputOutputKey design decision
Intake AgentRaw engagement request (email, form, forwarded message)Structured record: event name, date, org, requestor, format, audience, summaryExtract, don't interpret. The agent pulls fields but makes no judgment about priority
Triage AgentStructured record from IntakePriority score, category tag, recommended actionScoring rubric is explicit and auditable — no black-box ranking
Scheduling AgentTriaged request + calendar stateConflict check, logistics summary, proposed slotRead-only access to calendar. Proposes but never books
Briefing DrafterAccepted engagement + knowledge baseDraft briefing document with sourced sectionsEvery claim cites a source from the knowledge base. Unsourced sections flagged
Coverage EvaluatorDraft briefing + engagement contextCoverage score, gap list, suggested additionsMeasures what the brief missed, not just what it got right
Knowledge RetrievalQuery from any agentRelevant documents, prior engagement records, contextMaintains the reference corpus. Serves every other agent that needs background
OrchestratorEvents, completion signals, errorsTask routing, retry logic, status trackingStateless between runs. Picks up from the last known state, doesn't assume prior context

The one rule

Set before anything was built: the human is always the final sender. AI reads, extracts, triages, drafts and evaluates. A person reviews every extraction, makes every accept/decline decision, edits every briefing, and sends every communication. This wasn't a guardrail added later — it was the design constraint from day one. The same rule governed the earlier system I built at Microsoft.

The last line is the one I care about most. A system that handles 200+ items and sends nothing on its own is doing its job: it makes humans faster without taking their judgment away.

What carried forward from Microsoft

This system is the direct successor of the AI-powered engagement automation I built for a CVP's office at Microsoft. That earlier system proved the core pattern: AI handles reading, extraction and drafting; a shared list is the single source of truth; a human makes every final call.

What changed at scale:

  • One pipeline became seven agents. The Microsoft system was three sequential workflows. At 200+ items, I decomposed it into specialized agents that could run in parallel
  • Briefing production got its own evaluation loop. The Coverage Evaluator didn't exist in the Microsoft system — it was built because the failure mode I worried about most (a drafter that invents what it wasn't given) needed a systematic check
  • Knowledge retrieval became a shared service. Instead of each step pulling its own context, one agent maintains the reference corpus and serves every other agent that needs background
  • The orchestrator replaced manual sequencing. Routing, retries and failure handling moved from people monitoring queues to an agent that tracks state

What I chose not to build, and why

  • Didn't build a fully autonomous system. Kept humans in the loop at every decision point. An executive's calendar and communications are too consequential for unsupervised AI. The agents make the team faster, not independent of them
  • Didn't build a custom LLM. Used the platform's existing language models. The differentiation is in the agent architecture and the workflows, not the underlying model. Custom fine-tuning would have added months with marginal returns
  • Didn't build a UI. The agents run behind the existing tools the team already uses. No new interface to learn, no adoption friction. The best tool is one that improves the workflow people already have

What I'd build next

  • Cross-engagement pattern detection. An agent that spots recurring themes, repeat requestors and seasonal patterns across the full engagement history — shifting from reactive processing to proactive intelligence
  • Briefing quality feedback loop. Capture which parts of a briefing the executive actually used, and feed that back into the Briefing Drafter's priorities. The coverage metric today measures completeness; the next version should measure relevance
  • Agent portability. Package the agent definitions so the system can run on different orchestration platforms without rewriting the logic. The architecture shouldn't be locked to one vendor's tooling
