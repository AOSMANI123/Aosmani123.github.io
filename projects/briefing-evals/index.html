Briefing evals: does the AI make things up?

A small test suite for the failure I worry about most in AI-drafted briefings: a confident guess where the source was silent.

Type Independent workLanguage Python, no dependenciesCases 50, all fictionalVersion v2, October 31, 2026View the code

Short version. I build systems that draft executive briefings. In a briefing, a guess is worse than a blank. This suite gives a drafter 50 fictional engagement requests, each with a trap, and scores two things: did it pull out what was there, and did it fill in what wasn't? v2 turns it from a prompt test into a model-readiness test: repeated runs, a pass gate calibrated to measured noise, a side-by-side across model providers, and a check on the answer key itself.

Why this matters

A briefing drafter that's right 95% of the time sounds great until you ask what the other 5% looks like. If it leaves a field blank, someone fills it in. If it invents a moderator's name or carries last year's date forward, that error can reach an executive's prep with no warning. The second failure is the one to measure.

How it's scored

The drafter returns JSON with nine fields. Each field is scored as correct, missed (said UNKNOWN when the answer was there), wrong, or fabricated (filled in when the source was silent). The scorer also flags any number in the output that doesn't appear in the source.

MetricQuestion it answers
Recall on known fieldsDid it pull out what was actually there?
Fabrication rateOf the fields that were missing, how many did it fill in anyway?
Carried-over values v2Did a fact about a different event, year or person end up in this briefing?

The experiment

Same cases, two prompts. The naive one says "fill in the briefing details." The other states the rules I actually use: only this event, UNKNOWN when it isn't stated, the forwarder isn't the requestor, copy numbers as written.

Hypothesis The naive prompt fills in missing fields. Explicit rules bring fabrication close to zero without hurting recall.

What the failures actually were

On paper, the rules prompt cut fabrication from 83% to 8%. Reading each failure tells a more useful story.

Most of the naive prompt's "fabrications" were honest answers in the wrong words. Seven of the ten were the model declining to guess, writing Not specified or TBD instead of UNKNOWN. The naive prompt never asked for UNKNOWN, so this partly measures format, not honesty.

Three were real problems:

CaseWhat the model wroteWhy it matters
Virtual eventAudience: "40,000 (based on last year's stream)"The trap worked. The invented-number check missed it, because 40,000 is in the source, just about a different event.
No signatureRequestor: "Pacific Retail Association events team"No person signed, so the model put a team in a name field.
Vague crowdModerator: "Priya Nand"Priya is the emcee who introduces the keynote. A role mix-up, not an invented person.

Hypothesis check Partly confirmed. The rules prompt fixed two of the three real problems. The Priya Nand case survived both prompts, which points at the schema (there's no "introducer" field) rather than the prompt. And the rules weren't free: the model marked 4 stated fields UNKNOWN. A blank still beats a guess in an executive briefing, but it's a trade-off to measure, not assume.

The honest fabrication count for the naive prompt is closer to 3 of 12 than 10 of 12. The mocks proved the scorer works mechanically. The real run showed that working mechanically and measuring the right thing are different claims.

What v2 changed

Every item on the v1 "next" list is done, and building it turned up one more problem.

v1 problemv2 fix

Last year's 40,000 viewers slipped throughEach case can name values that belong to a different event, year or person. If one lands in a field, it's flagged as carried over

New: the v1 answer key contradicted itselfCase 02 said an introducer isn't a moderator, but two other cases counted an introducer and a keynote host as moderators. Both were fixed
Single runs can't support a gate--runs N, and a gate calibrated to measured noise (below)
Only one model providerAnthropic, OpenAI and Google drafters, with tokens, latency and cost per run

A gate people will trust

A pass gate that fails unchanged prompts gets turned off. One that misses real regressions is decorative. The v2 gate fails a change only when a metric moves more than run-to-run noise explains, and the allowance shrinks as either side runs more times.

I tested it on a simulated drafter before trusting it. The first design got less sensitive with more runs, so I replaced it. The shipped version, with 10 baseline runs:

Candidate1 run3 runs10 runs
Unchanged (false alarm rate)5%5%2%
Fabrication rate up 50%18%35%55%
Fabrication rate doubled57%90%100%

Share of 40 trials in which the gate failed the candidate. These numbers come from a simulation, not a model; the harness measures the real false-alarm rate once real runs exist. The setting I'd use: 10 baseline runs, 3 per change.

Sorting failures by what would fix them

Comparing two setups sorts every failure into four groups. Fixed by the candidate means the prompt change worked. Persistent means it fails no matter the prompt, so the problem is in the schema, the answer key or the model. Introduced is a regression. Flaky means run more before deciding. In v1, the emcee error persisted under both prompts and turned out to be a definition problem. v2 makes that call from data instead of by hand.

Checking the answer key

An eval is only as good as its answer key, and v1's had a contradiction nobody caught. v2 ships a labeling kit: a second person labels a 15-case sample without seeing the key, and the harness reports Cohen's kappa on "stated vs. not stated." The target is above 0.8. An AI review of all 50 keys found no wrong values and 14 edge cases, which are fixed. The human check is next, because a model reviewing a key written with a model's help shares its blind spots.

Status

Built and tested offline The cases, scorer, gate and labeling kit work, and 33 tests pass. Real-model runs across providers are next. The results will go into a one-page readiness memo: which model and prompt to ship, the evidence, and what would change the call.

Run it

python3 -m unittest discover -s tests
python3 evals.py --drafter mock-noisy --runs 10 --out runs/sim.json
python3 evals.py calibrate runs/sim.json

python3 evals.py --drafter anthropic --model <id> --prompt prompts/flag_gaps.txt --runs 10 --out runs/base.json
python3 evals.py --drafter anthropic --model <id> --prompt prompts/flag_gaps_v2.txt --runs 3 --out runs/cand.json
python3 evals.py compare runs/base.json runs/cand.json
python3 evals.py table runs/*.json

Limits

  • Fabrication coverage leans on one field: 26 of the 49 gaps are the moderator. Event name and ask are never missing. Read fabrication per field before drawing conclusions.
  • All 50 cases were written by one person with AI help. The human labeler check hasn't run yet.
  • Matching is word-level containment, so it can't catch an invented venue added next to the correct city.
  • It checks the fact block, not the prose of the briefing.
