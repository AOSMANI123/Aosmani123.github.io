Executive Writing Critic

A deterministic writing scorer that checks documents against an explicit executive writing bar: hedge words, passive voice, data density, adjective bloat, sentence variety, and lede placement. Seven rules, zero LLM calls, line-level findings.

Type CLI tool + web scorerBuilt October 2026Stack Python stdlib, vanilla JS

Short version. Most executive writing advice says "be clear" without telling you what to measure. This tool runs seven deterministic checks on pasted text and returns a letter grade with line-level findings. No LLM, no API key, no ambiguity about why something got flagged. What it checks

CheckWhat it measuresWhy it matters
Hedge / weasel wordsCount of "might," "possibly," "somewhat," "I think," and ten othersHedges signal the writer isn't sure of their own point. Executives stop reading.
Passive voiceSentences with passive construction as a share of totalPassive voice hides who is responsible for what. In a decision doc, that's fatal.
Data densityShare of sentences containing a number, stat, or metricClaims without data are opinions. Executive docs earn trust with evidence.
Adjective bloatAdjective count per sentence, flagging those above 3Adjective-heavy writing is vague. "A robust, scalable, world-class platform" says nothing.
Sentence length varianceStandard deviation and coefficient of variation of sentence word countsMonotonous rhythm puts people to sleep. Good writing varies pace.
Buried ledeWhether the first paragraph contains a recommendation, action verb, or numberIf the ask is on page two, it won't get read.
Opening specificityWhether paragraph one has a concrete noun, named entity, or numberAbstract openings lose the reader before you've said anything.

How the grade works

Each check gets a letter grade (A through F) based on where the measured rate falls against calibrated thresholds. The overall grade is the GPA of the individual checks: all A's = 4.0, a mix of B's and C's lands around 2.5. The tool is tuned for precision over recall: it flags only high-confidence findings to keep the signal-to-noise ratio useful.

Design decision: deterministic first

This tool uses pattern matching and heuristics, not an LLM. That's deliberate. Deterministic rules are fast, free, reproducible, and auditable. Every flag traces to a specific regex or threshold you can read in the source. The open question is whether rules alone catch enough real issues. If user testing shows they miss more than 15% of findings, the next version adds an LLM layer for semantic checks (tone, logical structure, argument quality). But rules go first, because you should know what simple measurement buys you before you spend on inference.

Run the CLI

python3 src/critic.py < your-doc.txt
python3 src/critic.py --file your-doc.txt
python3 src/critic.py --json --file your-doc.txt   # machine-readable

No dependencies beyond Python 3.6+ standard library.

What I chose not to build, and why

  • LLM-powered semantic analysis. Tone, argument structure, and logical coherence matter for executive writing. But LLMs are expensive, non-deterministic, and hard to debug when they produce a bad flag. Rules first. Measure whether they're enough. Add the LLM layer only if rules miss more than 15% of real issues in user testing.
  • Grammar checking. Tools like Grammarly already do this well. This tool targets the layer above grammar: is the writing shaped for the executive audience?
  • Document formatting analysis. Heading hierarchy, bullet structure, and whitespace matter. But they require document structure parsing that goes beyond plain text. That's a v2 concern.
